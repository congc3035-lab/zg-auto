# 架构设计

| 项 | 内容 |
|---|---|
| 版本 | V1.0 |
| 状态 | **已批准**（2026-08-28） |
| 形态 | 单文件 Tampermonkey 用户脚本 |
| 配套 | [需求规格](01-需求规格.md) |

本文档的首要目标不是描述如何实现，而是**限定代码只能在一个地方增长**。

## 一、选型：分层 + 任务注册表

采用**五层单向依赖架构**，配合**任务注册表**。所有业务扩张只允许发生在一个数组里，
其余四层代码量随任务数量增长保持恒定。

### 为什么是这个

脚本的本质是「一组彼此独立的动作，按固定节奏轮番执行，共享一条脆弱的网络协议和一个危险的全局状态」。

- **任务之间没有依赖** —— 领奖和开发属地互不影响，不需要工作流引擎，顺序循环足够。
- **协议脆弱且统一** —— 一次性 token、sid 位置敏感、静默失败。这些坑对每个任务都一样，
  必须收敛到一处，否则每加一个任务就多一份踩坑机会。
- **编队是共享的危险状态** —— 错误处理不当会污染下一次手动操作，必须由架构强制保护。

### 为什么不是别的

| 候选 | 不采用的理由 |
|---|---|
| 事件驱动 | 任务无依赖，引入事件后执行顺序变隐式，排查时看不出谁触发了谁 |
| 状态机 | 整体只有三态，过度设计。需要状态保护的只有编队，用作用域守卫即可 |
| 多文件 + 打包 | 三端（含手机）安装，引入构建步骤后分发困难。单文件是分发形态决定的硬约束 |
| 任务写成函数直接调用 | 最容易滑向的做法，也是膨胀起点：调度器逐渐堆满 if，加任务要改调度器 |

## 二、分层总览

依赖方向**严格单向向下**。下层禁止感知上层，禁止出现具体任务的名字。

| 层 | 名称 | 职责 | 禁止 |
|---|---|---|---|
| L5 | Runtime | 调度器、浮层、隐身 | 包含任何单任务的业务逻辑 |
| L4 | Tasks | Task 对象 + TASKS 注册表 | 直接发请求、直接改编队、写 localStorage |
| L3 | Domain | 编队守卫、资源读取、时间窗口 | 出现任何任务 id |
| L2 | Gateway | 唯一的游戏交互出口 | 新增第四个公开函数 |
| L1 | Core | HTTP、节流、解析、存储、日志 | 出现任何游戏词汇 |

**L4 是唯一允许随需求增长的层。**

协议坑只在 L2 出现一次。一次性 token、sid 位置、静默失败全部在 L2 内解决，
任务作者永远不需要知道这些坑存在 —— 这是新任务不会引入老 bug 的原因。

## 三、各层契约

### L1 Core

```
http.get(url)          → { ok, status, html, finalUrl }   // 含节流与重试
dom.parse(html)        → Document
dom.href(doc, re)      → string | null    // href 原文，已解码实体
dom.hrefAll(doc, re)   → string[]
dom.num(doc, re)       → number | null
store.get() / set(o)   → 单键读写 localStorage
log.push(entry)        → 结构化日志入队
sleep(ms)              → Promise
```

判据：把 L1 整段复制到另一个项目应当能直接用。

### L2 Gateway —— 最重要的一层

```
gw.read(path)                      → Document
gw.act(listPath, linkRe)           → ActResult   // 唯一写入口
gw.actAll(listPath, linkRe, max)   → ActResult[] // 每次重取 token

ActResult = { ok, matched, doc, url }
```

`act` 内部固定执行五步，任务无从干预：

1. GET 列表页，取得新鲜的 `_r`
2. 按正则找动作链接，**取 href 原文**，绝不手工拼接 sid
3. 节流等待（不低于 800 毫秒）后 GET 该链接
4. 检测响应是否为登录页 → 是则抛 `FatalError`
5. 返回结果文档供任务判断成败

> **铁律**：任何写操作必须经 `gw.act`。任务层出现 `http.get`、`fetch`、
> `location.href =` 一律视为违规。可用文本搜索机械检查。

### L3 Domain

```
resources.read()               → { orders, activity, copper, food }
formation.current()            → 'four' | 'solo' | 'other'
formation.ensure(kind)         → 切换到目标编队（幂等）
formation.withGuard(kind, fn)  → 切换 → 执行 fn → finally 切回 'four'
windows.isOpen(ranges)         → boolean   // 纯函数
```

### L4 Tasks

```
Task = {
  id:        'daily_claim',
  name:      '领周任务奖励',
  cadence:   'round' | 'daily',
  formation: 'four' | 'solo' | 'none',
  window:    [[12,13],[18,19]] | null,
  guard(ctx):  boolean,
  run(ctx):    Promise<TaskResult>
}

TaskResult = { status: 'done'|'skipped'|'failed', detail: string, count?: number }
ctx        = { gw, resources, windows, cfg, log }
```

## 四、调度算法

调度器只做三件事：自愈、按编队分组、顺序执行。它**不认识**任何具体任务。

```js
async function runRound() {
  if (!enabled) return;

  const ctx = await buildContext();
  await formation.ensure('four');        // 上轮若中断在 solo，这里修复

  const pass = TASKS.filter(t => shouldRun(t, ctx));
  const groupFour = pass.filter(t => t.formation !== 'solo');
  const groupSolo = pass.filter(t => t.formation === 'solo');

  for (const t of groupFour) await execute(t, ctx);

  if (groupSolo.length) {
    await formation.withGuard('solo', async () => {
      for (const t of groupSolo) await execute(t, ctx);
    });
  }

  await formation.ensure('four');
  store.set(ctx.state);
  panel.render();
}
```

「切一次编队、连打 N 次、再切回」**由架构自带**，不需要任务自己实现 ——
因为分组是按 `formation` 字段做的。将来新增单人阵任务自动享受同样的批处理。

### 统一错误边界

```js
async function execute(task, ctx) {
  try {
    const r = await task.run(ctx);
    log.push({ taskId: task.id, ...r });
  } catch (e) {
    if (e instanceof FatalError) throw e;   // 冒泡，停止整轮
    log.push({ taskId: task.id, status: 'failed', detail: e.message });
  }
}
```

## 五、配置外置

所有可变值集中在文件顶部 `CFG`。代码正文**禁止出现**裸路径、GUID、数字阈值。

```js
const CFG = {
  roundMs:      20 * 60 * 1000,
  throttleMs:   800,
  ordersFloor:  5,
  battlePath:   '/Game/Battle/Fight/102602',
  escortWindow: [[12,13],[18,19]],
  farmPriority: ['black','red','yellow'],
  dryRun:       true,                 // 默认开启
  stealth:      { enabled:false, title:'文档', hotkey:'Ctrl+Shift+G' },
  generals: {
    sima:  '723acde6-7f00-4378-a998-2f5baf76ca78',
    wang:  'fc4fa2cf-4775-4908-a4e6-12af041df335',
    yue:   'e01a0e22-6fa5-46d0-931f-efb4be56f4e4',

```

游戏改版时，八成的修复只需改 `CFG`，不必读代码逻辑。

## 六、防膨胀规则

六条**可机械检查**的硬规则。凡是需要靠人「记得遵守」的规则最终都会失效。

| 编号 | 规则 | 检查方法 |
|---|---|---|
| R1 | 新增任务只能新建 Task 对象并加入 `TASKS`，禁止改动 L1–L3 与调度器 | diff 若触及下层，说明抽象不足，**必须先重构再加任务** |
| R2 | L1–L3 禁止出现任何任务 id，禁止 `if (task.id === ...)` | 用 id 列表逐个搜索 L1–L3 代码段，命中即违规 |
| R3 | 单个 Task 的 `run` 不超过 40 行 | 超限说明是两件事，拆成两个 Task |
| R4 | L4、L5 禁止 `fetch`、`XMLHttpRequest`、`http.get`、`location.href =` | 文本搜索这几个词 |
| R5 | Gateway 公开函数冻结为 `read`、`act`、`actAll` | 想加第四个先问「是不是某任务想开特例」 |
| R6 | 单文件不超过 **1200 行**（不含注释与 UI 模板字符串） | 触顶禁止追加，必须先重构 |

R3 的拆分不增加调度器负担 —— 这正是注册表模式的意义。

## 七、测试策略

### 其一 · Dry-run（必做，默认开启）

`gw.act` 只记录「本应请求的 URL」而不真发，`gw.read` 照常。
可**完整走一遍全流程而不改动账号任何状态**。

每次改动后先跑一轮 dry-run 核对 URL 序列，再关掉执行。
**禁止跳过这一步直接实跑** —— 账号状态改坏了没有回滚。

### 其二 · 解析函数纯化（必做）

所有 HTML 解析写成纯函数：输入 HTML 字符串，输出值，不碰网络与 localStorage。
真实页面存进 `fixtures/`，可脱离浏览器验证。

游戏改版时对样本重跑解析函数即可定位是哪个页面变了，不必在浏览器里逐个试错。

### 其三 · 单任务执行

浮层为每个任务提供「单独执行」按钮，绕过 cadence 与 window 判断。

### 其四 · 日志可追溯

```
{ t: 1756368000000, taskId: 'battle', action: 'act',
  url: '/Game/Battle/Fight/102602?sid=***&_r=***',
  status: 'done', detail: '军功+60，剩余军令 6' }
```

`sid` 与 `_r` 在日志中**必须**脱敏，日志可能被截图外发。

## 八、错误分级

| 级别 | 典型情形 | 处理 | 中断整轮 |
|---|---|---|---|
| FatalError | sid 失效 | 停止全部，退出隐身，浮层红条 | 是 |
| TokenStale | 动作返回列表页 | 重取 token 重试 1 次 | 否 |
| Transient | 网络失败、超时 | 重试 2 次，间隔 2 秒 | 否 |
| TaskFailed | 战斗失败、次数用尽 | 记录后继续 | 否 |

只有 `FatalError` 向上冒泡。**单个任务永远不能拖垮整轮。**

## 九、文件内结构

单文件，内部按层顺序排列并用分隔注释标明。顺序即依赖顺序。

```
// ==UserScript== ... ==/UserScript==

//  ── CFG ────────────────  配置，全部可变值
//  ── L1 Core ────────────  http / dom / store / log / sleep
//  ── L2 Gateway ─────────  read / act / actAll + FatalError
//  ── L3 Domain ──────────  resources / formation / windows
//  ── L4 Tasks ───────────  各 Task 对象 + TASKS 注册表   ← 唯一增长区
//  ── L5 Runtime ─────────  scheduler / panel / stealth
//  ── Bootstrap ──────────  入口
```

分隔注释不是装饰。审查改动时先看它落在哪一段，
**落在 L4 之外的改动都需要额外说明理由**。

## 十、变更流程

| 变更类型 | 允许改动范围 | 需批准 |
|---|---|---|
| 新增一个日常任务 | 仅 L4 新增 Task + 注册 | 否 |
| 调整阈值、路径、GUID | 仅 `CFG` | 否 |
| 修复某任务的解析逻辑 | 该 Task 内部 | 否 |
| 新增 Gateway 函数 | L2 | **是** |
| 改动调度算法 | L5 | **是** |
| 触及 1200 行红线 | 全局重构 | **是** |
